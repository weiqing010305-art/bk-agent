# 对话收集信息与转账页面交接设计

设计日期：2026-10-20。以下保留当时设计；用户随后授权实施，2026-10-21 完成首版，当前实现范围与差异见 [验证记录](../../doc/research/2026-10-21-agent-validation.md)，不能将原设计条目一律视为已实现。

## 用户要求

> 把agent设计了，就是我们和agent对话，说我们要做的事，比如转账，然后agent问用户那些需要填写的信息，比如卡号和金额等，当实体提取的内容把所需的空全部填了，帮用户填写好然后跳转到转账的页面，只需要用户只需要点确认，以及输入密码，如果实体没有把空填完，就追问缺的信息

沿用 A-01/A-02 的并列入口、A-03 的服务端事实来源、A-04 的权限门禁。用户提出“确认并输入密码”为转账最低交互要求；风险策略需要额外验证时仍执行既有分级，不由 Agent 降级。

## 交互流程

1. 用户在助手里表达任务；一条消息可同时包含多个字段。
2. Agent 提取候选字段，由后端合并当前任务草稿、解析与校验。
3. 信息缺失、无效或有歧义时留在对话中，只询问需补充或澄清的内容。
4. 所有必填字段有效且无歧义后，后端创建待核对草稿，返回固定页面动作和草稿引用。
5. 前端自动打开转账页的“核对信息”步骤，已填写的内容完整展示且可修改。跳转不意味着执行。
6. 用户核对后点击“确认转账”，在独立验证界面输入支付密码；验证成功后由后端执行并出具回执。
7. 对话保留任务摘要及“查看这笔转账”，回到对话不会丢失任务或新建同一笔交易。

示例（假定收款人已唯一匹配且只有一个有效默认付款账户）：

- 用户：“给王佩兰转一笔。”
- 助手：“转多少钱？”
- 用户：“500，备注房租。”
- 助手：“已填写好，接下来请核对并确认。”
- 自动打开转账核对页：收款人、银行和卡号尾号、付款账户、¥500.00、备注。
- 用户确认 → 输入密码 → 后端返回回执。

若出现同名收款人，提供脱敏候选卡片让用户选择；不拿首个模糊匹配结果直接填入。陌生收款人按业务接口要求收集完整卡号、姓名等；银行与身份匹配结果只能来自可用的权威接口。格式检查不等于身份核验。

## 字段与追问规则

| 字段 | 来源与处理 | 追问条件 |
| --- | --- | --- |
| 转账方式 | 本版仅人民币即时转给他人 | 预约、AA、跨币种请求应明确交接或说明当前能力，不静默改成即时转账 |
| 收款账户 | 用户选择已存收款人，或提供完整卡号 | 缺失、同名多账户、号码无效或查询未命中 |
| 收款人姓名 | 已存记录/核验结果；新收款人按接口要求填写 | 必需但缺失，或姓名与核验结果冲突 |
| 付款账户 | 用户明确指定；否则使用有效的用户默认账户并在核对页展示 | 多账户且无明确默认，或账户不可用 |
| 金额与币种 | 原文金额由确定性解析器转换为整数分；本版限定人民币 | 缺失、非正数、精度超限、单位不清或超出可用余额/限额 |
| 备注 | 用户明确提供的可选字段 | 不因可选备注为空而追问；超长时让用户修改 |
| 密码/验证码 | 独立验证组件直达认证后端 | 永不作为对话槽位，永不要求用户在聊天中填写 |

问法顺序优先解决收款人，再金额，最后付款账户；每次一个简短问题，用户可一次补多个字段。已有效填写的字段不重复询问。

“改成五百”更新金额；“不是王佩兰，是李明”替换收款人并重新核验。发生矛盾但没有明确更正语义时澄清，不能仅凭模型置信度自动决定。

“取消”终止当前未执行任务；“再转一笔”显式新建任务。临时查询余额可保留草稿；恢复时重新校验。新聊天不继承旧聊天的未完成指令，历史恢复也不自动执行。

## 实现职责与状态

采用“一个对话 Agent + 确定性任务状态机 + 受限业务工具”。优先于每项业务各建独立 Agent，减少状态和权限的分散；相比纯规则方案，模型主要补足自然表达和多轮更正理解。

- 模型：输出受限意图、候选字段、更正/取消动作及原消息证据引用，不生成余额、真实收款人身份或交易结果。
- 草稿服务：存储任务状态，校验字段来源、权限、格式及冲突；模型补丁必须经过服务校验才能进入业务数据模型。
- 业务服务：查询账户与收款人，计算金额和限额，准备待核对操作。页面与聊天共用同一结果。
- 前端：渲染服务端数据引用，执行白名单页面交接；不用模型生成 HTML、URL 或选择器来操纵页面。
- 认证与执行：独立于模型工具权限，验证用户本人操作、绑定具体交易并生成回执。

状态顺序：

`COLLECTING → VALIDATING → READY_FOR_REVIEW → AWAITING_AUTH → PROCESSING → SUCCEEDED`

校验发现问题回到 `COLLECTING`；支持 `CANCELLED / EXPIRED / FAILED / RESULT_UNKNOWN`。结果未知时查询原操作，不创建新交易或显示成功。

建议任务记录包含：taskId、ownerId、conversationId、intent、version、各字段候选值与来源、校验状态、missingFields、冲突项、operationId、expiresAt。ownerId 由服务端会话推导，不接受模型提交。

模型可请求的工具限于读取授权账户/收款候选、更新草稿、校验草稿和准备核对。确认、密码验证和执行接口不向模型开放。

跳转仅传 taskId/draftId 等不含敏感值的引用；转账页从后端加载并校验所属用户、版本和有效期。完整卡号、金额和认证数据不拼进 URL。

## 准确性与安全边界

- “字段齐全”同时要求：必填项存在、格式有效、账户匹配、无冲突、业务校验通过。模型不能自行宣布已核验。
- 收款人、金额、付款账户等关键字段改变，旧核对结果和认证授权立即失效；页面编辑与聊天修改使用同一版本控制，避免旧响应覆盖新值。
- 金额用整数分；卡号用字符串；单位转换使用确定性规则。卡号输入可在本地转换为服务端引用，模型与普通聊天历史只保留脱敏描述。
- 如果用户意外在聊天输入密码，不能仅靠提示词处理；发送模型前需进行敏感输入拦截/最小化处理。应承认自由文本无法保证识别所有秘密，不声称绝对防泄漏。
- 密码不进入提示词、对话历史、草稿、日志或浏览器持久化；验证组件直接提交认证服务，失败次数限制、会话绑定与凭据保护由服务端实现。
- 验证授权绑定操作 ID、参数摘要、版本和有效期。交易执行时复查余额、账户权限和限额；连续点击与重试使用同一幂等键。
- 工具响应、备注和检索文本均不能赋予权限；“用户已授权”等自然语言不等于认证结果。拒绝跨用户草稿、越权工具及绕过验证请求。
- 自动跳转只发生于当前聊天的当前任务。旧会话晚到响应只更新其任务状态，不抢走用户正在看的页面。

## 与现有工程的衔接及缺口

- `src/state/useTurnRunner.js`：现为规则解析；后续改为对话回合入口，发送当前任务引用并接收追问或交接事件。
- `src/state/useTransferFlow.js`：已有部分槽位预填，但使用首个姓名模糊匹配；需改为后端唯一匹配或显式选择，并接入跨回合草稿。
- `src/views/pages/transfer.jsx`：目前从本地空草稿开始；新增按草稿引用加载并落到核对步骤，保留原手动入口。
- `backend/app.py`：已有整数分、操作版本/摘要、幂等及验证码流程；需要新增受限任务草稿服务、后端统一风险检查、付款账户约束及真实的支付密码验证能力。
- 当前转账验证是返回演示码的流程，并非支付密码认证；不得只修改输入框标题后宣称实现。竞赛测试只能使用专用虚拟账户和测试密码。
- 当前转账主要使用单一账户及已登记收款目录；多付款账户、陌生银行卡身份核验均不能假定已有真实支持。

这些均是后续实施项；本设计不代表已完成接入或通过安全评估。

## 验收与安全自评证据

| 场景 | 必须达到的行为 |
| --- | --- |
| “转账” → 卡号 → 金额 | 连续补齐同一草稿，不丢字段，缺项时不跳转 |
| 一句话包含全部字段 | 校验通过后直接到核对页，不重复问 |
| 同名、多账户、歧义金额 | 先澄清，不猜选 |
| 已核对后改金额/收款人 | 重新核对与授权，旧授权不能执行 |
| 用户只在聊天说“确认” | 不能代替页面确认及密码验证 |
| 越权草稿、伪造授权、恶意备注 | 后端拒绝，未产生扣款 |
| 切换聊天、刷新、重复点击、超时 | 不串单、不重复扣款；未知结果只查询原操作 |
| 密码输入与日志检查 | 模型请求、会话存储和普通日志不含认证秘密 |
| 账本与回执一致性 | 收付款对象、金额、币种、状态与数据库一致 |

安全自评报告逐项记录实现位置、测试样例、实际结果和已知风险；设计项和待实现项不标成“已通过”。本次仅设计，未运行上述功能或安全测试。
