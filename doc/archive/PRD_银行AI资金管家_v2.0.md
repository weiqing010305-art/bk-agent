| 决策项 | 本版结论 | 状态 |
|---|---|---|
| 产品方向 | 围绕个人资金安排提供银行服务，具备分析、规划、授权执行能力 | 用户已认可方向 |

“保留四项功能”指保留完整的业务模块；模块中的核心能力和扩展能力在本文中分别列出，避免把所有子功能都默认为首版必做。

## 2 产品定位与目标用户

### 2.1 一句话定位

银行 AI 资金管家通过自然语言理解个人客户的用钱需求，结合账户、账单和周期支出生成可解释的资金方案，并在分级授权下完成银行操作。

用户可以直接办理“给房东转 3000 元”，也可以提出“下个月买电脑，但不能影响房租和还款”。系统既支持单项业务，也支持持续跟踪的资金计划。

### 2.2 主要用户

首版聚焦有银行账户、周期性支出和阶段性资金目标的个人客户。以工资收入用户作为主要演示画像，同时允许用户手动补充不固定收入。产品只分析已接入或用户补充的数据，首页明确账户覆盖范围。

| 用户情境 | 当前困难 | 产品应提供的帮助 |
|---|---|---|
| 日常办理业务 | 转账、查账、管理卡片需要寻找多个入口 | 自然语言发起，结构化核对，清晰展示结果 |
| 工资前资金紧张 | 看到当前余额，却不知道到期支出会集中在哪一天 | 未来现金流、余额低点与缺口原因 |
| 多项自动扣费 | 不清楚哪些扣费会继续发生、哪些能够取消 | 周期扣费识别、协议核查、提醒及可支持的取消操作 |
| 计划大额消费或储蓄 | 不知道目标金额和时间是否可行 | 方案试算、调整建议、执行任务与进度 |
| 卡片异常或遗失 | 需要快速找到对应卡片并处理 | 核查交易、临时冻结或挂失、查看处理状态 |

### 2.3 产品目标

1. 常见银行操作能够从一句自然语言进入明确的业务流程，减少查找入口和重复填表。
2. 每项重要分析都可以追溯到交易、账单或用户设定，用户能够修正错误假设。
3. 用户在执行资金操作前能看见对近期账单和资金目标的影响。
4. 资金计划能够转化为可跟踪的任务，执行状态与银行返回结果一致。
5. 所有写操作均有对应授权和记录；遇到歧义、数据缺失或未知结果时不擅自执行。

以上是待验证的产品目标，不预先宣称已提升转化率、节省固定比例操作时间或达到行业领先水平。

## 3 比赛契合度与创新取舍

### 3.1 与赛题的关系

本地《大赛问题整理.docx》中的赛题截图写明：至少覆盖三个核心场景、鼓励全覆盖；同时强调自然语言理解、任务规划、权限分级和安全机制。此处依据本地留存材料，不代表已核验后续赛事公告。对 Web 渠道的判断依据是截图中的“APP、IM 等渠道”，该表述未在所见材料中将 IM 列为唯一渠道；提交前需对照届时正式要求复核。

本版保留的四项功能对应四个原始业务场景，资金计划进一步展示跨场景联动。六个产品模块不等于声称覆盖了原始六类场景，其中理财操作不在本版范围。

| 赛题能力 | 产品落点 | 可展示证据 |
|---|---|---|
| 智能转账 | 收款人识别、核对、模拟转账、定时任务 | 转账回执及任务状态 |
| 账单分析 | 分类、趋势、异常候选、交易追溯 | 图表到明细的核查过程 |
| 订阅代扣管理 | 周期扣费识别、提醒、受支持的协议取消 | 候选识别到协议状态的变化 |
| 卡片管理 | 状态查询、冻结、解冻、挂失 | 强验证及卡片状态变化 |
| 跨场景联动 | 目标资金计划调用账单分析、预测和转账能力 | 多步骤计划及中断恢复 |
| 意图理解与规划 | 识别模糊对象、追问关键字段、生成和调整任务 | 用户修改需求后的计划变化 |
| 权限和安全 | 分级确认、验证、数据访问边界、操作记录 | 正常操作和越权尝试的不同结果 |

### 3.2 两项新增功能的选择理由

本版考虑了现金流预警、目标资金计划、泛化金融问答、优惠推荐和外部生活消费代办。前两项更能复用账户、账单、转账数据，具有明确的用户决策价值，也适合用 Web 展示连续变化。其余候选暂不纳入。

| 新增能力 | 用户得到的新价值 | 与已有功能的边界 | 可实现的创意点 |
|---|---|---|---|
| 未来现金流预警 | 提前看见某一天的资金压力 | 账单分析解释过去，现金流预警预测未来 | 展示“这笔钱现在花掉，会影响哪一天”，支持对比不同假设 |
| 目标资金计划 | 把用钱愿望落实为安排和任务 | 预测提供信息，目标计划管理目标、资金分配及执行 | 调整金额或日期即看到可行性变化；多个目标争用同一笔钱时提示冲突 |

这两项是本产品的体验差异点，不宣称它们属于市场首创。

## 4 功能范围与版本优先级

P0 为首个完整比赛版本必须具备的能力，六个模块均需有可用闭环。P1 为主流程稳定后的增强能力，不计入 P0 完成标准。

| 编号 | 模块 | P0 必做 | P1 增强 |
|---|---|---|---|
| F1 | 智能转账 | 按已绑定联系人姓名或手机号检索、备注转账、立即转账、到期确认式定时转账 | AA 账单及收款进度、受限的预授权定时执行 |
| F2 | 订阅管理 | 周期扣费候选、协议核对、续费提醒、受支持协议的模拟取消 | 扣费涨价和疑似重复订阅提示 |
| F3 | 账单分析 | 分类与纠正、月度分析、区间对比、异常候选、明细追溯 | 年度报告、更多自定义维度 |
| F4 | 卡片管理 | 卡片状态、临时冻结、解冻、挂失、关联交易查询 | 交易限额调整、交易渠道限制、模拟卡申请及进度 |
| F5 | 未来现金流预警 | 30 天预测、账单日历、余额低点、缺口解释、操作前影响试算 | 多种收入延迟情景、90 天预测 |
| F6 | 目标资金计划 | 目标创建、两种安排方案、资金分配、目标冲突检测、转账任务、变化后重新规划 | 更长周期目标、用户主动授权的限额规则 |

跨模块必做能力包括 Web 页面、AI 侧栏、任务中心、确认与模拟强验证、站内通知、操作记录、样例账户切换及可复现演示。

## 5 Web 信息架构与交互原则

### 5.1 页面结构

| 页面 | 用户主要任务 | 核心内容 |
|---|---|---|
| 首页 | 知道目前需要关注什么 | 可用余额、数据范围与更新时间、未来余额低点、近期账单、待确认任务、目标摘要 |
| 转账 | 办理和追踪资金划转 | 收付款账户、联系人、金额、备注、定时任务、回执 |
| 账单 | 理解历史收支 | 分类图、区间对比、变化解释、异常候选、交易明细 |
| 订阅 | 管理持续扣费 | 已验证协议、疑似周期扣费、预计续费、取消能力与处理状态 |
| 卡片 | 管理具体卡片 | 脱敏卡号、卡片状态、关联交易、可办理操作 |
| 资金计划 | 看未来并安排目标 | 收支日历、余额曲线、情景切换、目标列表、方案比较 |
| 任务中心 | 查看和处理计划步骤 | 待确认、待执行、处理中、成功、失败、结果待核实、取消和过期 |

F5 和 F6 共用“资金计划”页面，分别承担未来现金流与目标规划两个区域。模块数量不要求与导航数量一一对应。

### 5.2 AI 与页面协同

AI 侧栏在各业务页面可用，用户可以输入自然语言，也可以直接操作表单。两种入口修改的是同一份业务草稿，金额、对象、日期和任务状态保持同步。

用户主动选择一笔交易或一张卡片时，可以将该对象交给 AI；页面应显示当前关联对象。浏览到某张卡片不等于授权 AI 修改它。

分析结果以图表、证据和简短说明展示。写操作必须进入结构化确认卡；一句含糊的“好的”不自动批准多个待办任务。确认卡应显示本次批准的具体操作及范围。

### 5.3 结果与通知

每项业务提供直接结果：查询展示数据及时间，执行展示回执或真实错误，预测展示假设，计划展示下一步。

首版采用持久化站内通知。用户关闭浏览器后，到期任务仍保留，重新进入后能够查看；不把站内提醒描述成短信或系统推送。相同问题未发生实质变化时不反复通知，余额跌破新阈值、到期、执行失败或需要用户处理时才新增提醒。

用于评委查看的决策依据与操作记录单独提供演示视图。普通页面不展示底层提示词、框架名称或模型内部推理。

## 6 F1 智能转账

### 6.1 用户故事

“给房东转 3000 元，备注十月房租。”用户希望快速找到正确联系人，核对信息并获得明确回执。

### 6.2 P0 需求

| 编号 | 需求 | 产品行为 |
|---|---|---|
| F1-01 | 识别收款人 | 只在用户可访问、已有账户绑定关系的联系人中按姓名、别名或手机号检索；手机号本身不被视为银行收款账户 |
| F1-02 | 处理歧义 | 同名、未绑定或多账户时列出脱敏候选，要求选择；不能擅自选第一项 |
| F1-03 | 完整核对 | 展示付款账户、收款人及账户尾号、金额、备注、费用和到账说明；未知项明确显示未知 |
| F1-04 | 立即转账 | 信息完整后分级授权，执行并展示模拟银行回执 |
| F1-05 | 定时转账 | 创建任务时确认对象、金额、日期及到期窗口；默认到期后再次确认执行，错过窗口则过期 |
| F1-06 | 修改与取消 | 未执行任务可修改或取消；修改金额、对象、付款账户或日期后，旧授权失效 |
| F1-07 | 操作前试算 | 展示对近期余额和目标分配的影响，允许展开计算依据 |

金额、收款账户等来自历史的字段必须在确认卡中标明“沿用上次记录”，由用户核对。没有附言不阻断转账。

### 6.3 状态和边界

余额不足、卡片状态不允许、缺少授权或验证失败时禁止执行。未来可能资金紧张属于预测提示，与当前银行余额不足分开处理：普通提示允许用户阅读后继续；用户明确设置的计划约束，需要先修改约束或重新批准例外，不能被 AI 悄悄忽略。

重复点击确认不得产生重复交易。银行结果未知时展示“结果待核实”，先查询原交易，不发起第二笔转账。已成功交易不支持通过删除计划直接撤销。

P1 的 AA 功能生成各方应付金额、用户可分享的收款说明及匹配进度；不得扣划其他人的账户，也不默认向联系人发送消息。

### 6.4 验收

能完成一笔正常转账、一笔超过演示累计阈值的强验证转账、一笔到期确认式定时转账；同名对象得到澄清；重复确认只产生一笔交易；结果未知不会被描述为成功或直接重转。

## 7 F2 订阅与代扣管理

### 7.1 用户故事

“下个月有哪些自动扣费？这个会员我不想再续了。”用户希望识别持续支出并在有能力的范围内处理。

### 7.2 P0 需求

| 编号 | 需求 | 产品行为 |
|---|---|---|
| F2-01 | 识别周期扣费 | 根据历史商户、时间间隔、金额范围提出候选，展示支持判断的交易 |
| F2-02 | 区分证据 | 有有效代扣协议的显示“已核实”；仅从流水推断的显示“疑似周期扣费” |
| F2-03 | 用户纠正 | 用户可确认、修改周期与预计金额，或标记非订阅；原始交易不被修改 |
| F2-04 | 续费提醒 | 已知日期按协议显示，推测日期明确标注预计；可设置提前提醒和关闭提醒 |
| F2-05 | 能力明确 | 分别显示“可终止银行代扣协议”“可取消商户订阅”“需要前往服务方办理”，依据接口能力决定 |
| F2-06 | 取消流程 | 展示对象、范围、生效时间及已知影响，用户确认后调用受支持的模拟接口，返回明确状态 |
| F2-07 | 预测联动 | 取消成功且生效日期已确认后，从该日期起调整预测；处理中或结果未知时保留原支出 |

### 7.3 状态和边界

终止银行代扣协议不等于解除商户服务合同，不代表已有欠款消失或必然不会通过其他渠道扣费。页面和 Agent 必须使用接口实际支持的动作名称。

“一键取消”仅限沙箱明确支持的协议或商户。未接入的服务提供办理指引，并标记“待用户处理”；用户点击办理入口不等于取消完成。

只凭流水无法判断用户有没有使用某个会员，不输出“你三个月没用过”的结论。重复订阅只标为候选，交由用户核查。

### 7.4 验收

样例数据同时包含已核实协议、疑似周期扣费和不支持直接取消的服务。能够展示依据、完成一次受支持的模拟取消，并验证生效日期前后的预测变化。取消失败或未知时不能提前计入节省金额。

## 8 F3 账单分析

### 8.1 用户故事

“这个月为什么多花了 800 元？”用户希望看见具体原因，并能核对交易。

### 8.2 P0 需求

| 编号 | 需求 | 产品行为 |
|---|---|---|
| F3-01 | 分类统计 | 展示收入、支出、类别及未分类交易；允许用户修改分类 |
| F3-02 | 区间比较 | 支持月度及自定义日期比较；未结束月份默认与上月相同天数比较，说明比较范围 |
| F3-03 | 解释变化 | 将变化落实到类别、商户和交易；支持从图表跳到明细 |
| F3-04 | 异常候选 | 提示与历史相比明显变化的金额、频率或商户，说明触发原因 |
| F3-05 | 自然语言查询 | 支持“上个月交通花多少”“找出这笔扣费”，金额来自账单计算 |
| F3-06 | 处理入口 | 对周期扣费进入订阅页，对可疑交易进入对应卡片核查，对资金压力进入未来现金流 |

### 8.3 统计口径

本人已接入账户之间的划转不计为新增收入或消费；跨账户报告同时排除对应两端，单账户报告保留流入流出。

能够关联的退款与原交易关联展示，同时支持查看原消费及净支出。不确定能否关联时保持原始记录，不强行冲抵。

信用卡消费与后续还款不能同时计入消费总额。消费报告记录消费，资金预测记录还款资金流出；两者用途和口径分别说明。

异常提示表示“值得核查”，不能仅凭分析直接断言诈骗，也不自动冻结卡片。明细不足时只输出可支持的分析范围。

### 8.4 验收

任一图表金额可追溯到明细并正确汇总；本人账户互转和信用卡还款不造成重复消费；修改分类后统计同步变化；异常说明能定位到具体交易；缺数据时不编造原因。

## 9 F4 卡片管理

### 9.1 用户故事

“尾号 1234 的卡找不到了，先暂停使用。”系统需要识别卡片，说明冻结影响，完成授权后处理。

### 9.2 P0 需求

| 编号 | 需求 | 产品行为 |
|---|---|---|
| F4-01 | 卡片总览 | 展示脱敏卡号、类型、所属账户、卡片状态、已支持的操作 |
| F4-02 | 关联查询 | 查看对应卡片近期交易和已知代扣关系 |
| F4-03 | 临时冻结 | 展示该模拟银行支持的限制范围，确认后暂停对应交易能力 |
| F4-04 | 解冻 | 重新核查状态并强验证，恢复接口明确支持的能力 |
| F4-05 | 挂失 | 展示与临时冻结的区别，强验证后提交并查询最终状态 |
| F4-06 | 影响说明 | 提示可能受影响的已知任务、代扣或计划，用户可以进入调整 |

### 9.3 状态和边界

不假定冻结银行卡能够阻止全部账户级代扣、退款或已在途交易。沙箱须定义卡级支付、账户级转账和代扣分别受哪些状态约束，页面按该规则说明。

卡片状态以服务端查询结果为准，不能只在前端换标签。冻结与挂失属于不同操作；解冻不能被表述为所有挂失业务的恢复方式。

P1 的“额度调整”默认指用户在银行允许范围内调整交易限额，不把信用授信额度调整视为即时批准。模拟卡申请需有资料检查和申请状态，不承诺提交即发卡。

### 9.4 验收

多张卡时能够明确选择对象；完成冻结和解冻后重新查询状态一致；挂失须强验证；关联任务得到影响提示；不把银行未支持的解除操作展示为可执行。

## 10 F5 未来现金流预警

### 10.1 用户故事与价值

“我现在还有 9000 元，工资前花 6000 元买电脑会不会影响还款？”用户需要同时看到支出的时间顺序和后果。

本功能提供未来 30 天的账户资金预测，并支持对一笔拟议支出进行试算。创意体现在把当前操作映射到未来具体日期的影响，让提醒可解释、可处理。

### 10.2 输入与可信程度

| 数据 | 处理方式 |
|---|---|
| 当前可用余额 | 从已接入账户读取，附更新时间；不可用或受限资金不直接算入可支付资金 |
| 已知未来支出 | 已出账账单、有效代扣协议、已创建转账任务，保留来源和日期 |
| 预计收入 | 历史工资规律或用户填写；到账前始终为预计，不因用户确认预期就变成银行事实 |
| 日常生活预算 | 用户填写，或根据历史生成候选后由用户调整；说明估算区间 |
| 储蓄目标分配 | 用于计算尚未分配资金，不冒充实际扣款或账户冻结 |
| 其他账户和现金 | 未接入部分默认不纳入；用户补充的金额明确标为手动数据 |

默认同时提供“包含预计收入”和“不计未到账收入”的两种视图，用来显露收入不确定性，不输出虚构的概率精度。

### 10.3 核心规则

按日预测余额等于当前可用余额，加上截至当日纳入该情景的未来流入，再减去未来流出。页面同时显示是否采用预计收入和生活预算。

资金预测同时提供单账户与合并视图。本人账户互转影响各账户的可支付能力，但不改变合并资金总额。不能用所有账户合计余额掩盖实际扣款账户余额不足。

尚未分配资金等于相应范围内的预计余额，减去尚未被上述现金流扣除的目标预留额度。账单、转账任务、储蓄分配需关联去重，不能以不同名称重复扣减。同日入账与扣款先后未知时提示顺序不确定，并按先扣款的保守情景检查当日压力。

### 10.4 P0 需求

| 编号 | 需求 | 产品行为 |
|---|---|---|
| F5-01 | 未来日历 | 按日期呈现已知支出、预计收入和计划任务；点击查看来源 |
| F5-02 | 余额低点 | 展示预计最低余额、日期，以及低于用户设定生活缓冲的情况 |
| F5-03 | 缺口解释 | 列出造成缺口的项目及合计，说明其中哪些金额是估计值 |
| F5-04 | 操作试算 | 在转账或目标规划中展示执行前后变化，不因试算生成真实交易 |
| F5-05 | 假设编辑 | 允许调整预计收入日期、日常预算和缓冲要求，重新计算 |
| F5-06 | 处理建议 | 优先提供推迟可选支出、降低目标金额、从本人可用账户调配等选项；不能擅自推迟已到期的还款义务 |
| F5-07 | 变化通知 | 账单金额或到账情况变化影响预测时，更新结果并通知受影响事项 |

### 10.5 边界和验收

预测不提供确定收益、必然到账或永不透支的保证。不把未确定取消的订阅、未发生的退款算成确定可用资金，不主动推荐借贷作为填补缺口的默认方案。

固定样例中，系统能正确算出低点、日期和差额，并展示对应来源。改变工资日期、账单金额或付款账户时，预测正确更新。日期不确定或数据过旧时明确提示，执行前重新核对实际余额。

## 11 F6 目标资金计划

### 11.1 用户故事与价值

“我想买 6000 元的电脑，最晚下月底，房租和还款必须先留够。”用户输入目标和约束后，系统生成可以比较、修改和执行的安排。

目标资金计划复用现金流预测，但额外管理目标、资金分配、优先级、任务和后续变化。创意体现在可交互的方案试算，以及多个目标争用同一笔钱时的冲突解释。

### 11.2 目标与约束

每个目标至少包含名称、目标金额、期望完成日期、资金范围、已分配金额和优先级。缺失的关键字段先澄清；如果用户不知道日期，可以选择先估算最早可行日期，再确认目标。

约束包括必要账单、用户设定的生活缓冲和已有资金目标。用户可以调整约束，但 AI 不能为使方案“看起来可行”而私自删除约束、假设收入上涨或把未知收入当成到账。

### 11.3 P0 需求

| 编号 | 需求 | 产品行为 |
|---|---|---|
| F6-01 | 自然语言建目标 | 抽取金额、时间与限制，生成可编辑目标卡 |
| F6-02 | 方案比较 | 数据允许时提供“保留目标金额，调整日期”和“保留日期，调整金额”两种方案；不可行时说明缺口，不强行输出两个可行方案 |
| F6-03 | 资金分配 | 用户确认某笔资金归属某个目标；展示为计划分配，不宣称银行资金已锁定 |
| F6-04 | 冲突检查 | 同一资金不能同时完整计入多个目标；冲突时显示受影响目标和差额，由用户调整优先级 |
| F6-05 | 生成任务 | 支持分阶段存钱、本人账户划转、到期提醒和经用户选择的代扣处理；每项任务展示对象、日期、金额和授权要求 |
| F6-06 | 授权执行 | 目标确认只批准计划内容，不自动授权所有资金操作；具体写操作另行确认，达到条件时强验证 |
| F6-07 | 跟踪变化 | 计划所依赖的工资未到账、发生新增大额支出或卡片状态变化时，暂停受影响的未执行步骤并提出新方案 |
| F6-08 | 调整及终止 | 可修改、暂停、恢复或结束目标；明确哪些步骤已完成、哪些可取消、哪些需要另行处理 |

### 11.4 资金归属和完成状态

“计划分配”是资金用途标记，不具备银行冻结效果。若用户选择将资金实际转入本人另一账户，必须通过智能转账完成，并将回执关联到目标。

同一笔转账不能既作为合并资金的支出，又再次完整扣除为同一目标的预留。目标账户中的钱依然属于用户资产；“已存入”“已分配”“尚需积累”分别展示。

目标状态至少区分草稿、进行中、需调整、暂停、资金已备齐和已结束。资金已备齐不等于已购买电脑。外部购物不在产品能力内，用户可自行标记目标结束，系统标明这是用户确认。

银行操作结果未知时，依赖该操作的步骤不得继续执行。多步骤计划失败后保留已成功步骤，不宣称整体回滚；涉及返还资金时，需要新建并授权相应交易。

### 11.5 验收

至少演示一个分两阶段完成的目标、两个目标争用资金、一次因预计收入未到账而暂停并重新规划。调整金额或日期后，方案及任务同步更新；取消目标不撤销已完成转账；不自动授权后续支出。

## 12 跨模块任务与权限规则

### 12.1 任务状态

任务从草稿进入待确认，授权后可进入待执行或处理中。处理结果分别为成功、失败或结果待核实；未执行任务可以取消或过期。

定时转账的计划创建和交易执行属于两个阶段。到期时重新检查账户、金额、余额、当日累计、授权时效和相关卡片限制；P0 需再次向用户请求执行确认。没有用户响应时不得扣款。

对未知结果保留原交易标识并核查；对明确失败说明原因和可行的后续动作。重试不能重复执行已成功步骤。

### 12.2 分级授权

下表为本比赛沙箱的产品策略，金额示例沿用本地赛题中的日累计 1000 元阈值，不表述为真实银行通用制度。只读与写入均须先校验用户身份和数据访问范围。

| 等级 | 操作示例 | 用户体验 |
|---|---|---|
| 绿色 | 余额查询、账单分析、卡片状态、现金流试算、方案草稿 | 在已登录且有访问权限的情况下直接返回结果 |
| 黄色 | 日累计不超过 1000 元的转账、订阅协议查询与取消、卡片临时冻结、目标计划保存 | 展示具体内容和影响，用户明确确认 |
| 红色 | 日累计超过 1000 元的转账、卡片挂失、解冻及其他提高风险暴露的操作 | 展示详情并进行模拟强验证 |

订阅协议查询按本地赛题表的黄色示例处理，不能因名称含“查询”就自行降级。其他新能力按实际读写和影响分类；红色操作不因模型建议、目标已保存或用户说“以后都不用问”而绕过验证。

同一用户所有会话中的受策略约束转账共同累计。执行中的资金和额度需防止被并发重复占用；明确失败后释放占用，结果未知时先核查。界面应显示本次操作的判定原因。

强验证仅为比赛模拟机制，界面不声称已经发送真实短信或完成人脸识别。金额、对象、账户等关键字段变化后，旧确认和旧验证不能用于新交易。

### 12.3 安全和审计的产品要求

1. 模型可提出操作请求，最终执行必须通过独立权限检查；页面按钮和 AI 入口受同一规则约束。
2. 他人账户、其他用户会话中的对象不得访问或操作。知道卡号、任务编号不等于有权限。
3. 账单备注、商户描述或外部文本中夹带的指令不能成为新的用户授权。工具返回内容也不能自行提升权限。
4. 金额、账户状态、交易结果来自结构化银行数据；预测和解释不得覆盖业务事实。数据缺失时如实提示。
5. 记录请求摘要、关键参数来源、确认版本、权限结果、验证是否通过、调用对象、时间和执行结果。敏感信息脱敏，不记录验证码、密钥或模型内部推理原文。
6. 连续工具故障暂停受影响操作并说明恢复方式，查询能力尽量可用。异常限流的具体阈值由技术方案验证，不直接沿用“多次正常红色操作即冻结账户”的旧规则。
7. 需要人工处理时显示明确指引及可导出的操作编号；无真实人工服务接入时，不声称已转接成功。

## 13 数据范围与演示约束

首版不依赖真实银行生产接口。模拟服务需能够真实改变其内部账户余额、交易、协议和卡片状态，前端查询与执行结果保持一致，不能只展示预制成功文案。

| 数据对象 | 必要信息 | 主要用途 |
|---|---|---|
| 用户与账户 | 用户归属、账户类型、可用余额、更新时间 | 权限、转账、预测 |
| 卡片 | 所属账户、脱敏标识、状态、操作能力 | 卡片管理和影响分析 |
| 交易 | 金额、币种、时间、状态、关联方、分类、转账或退款关联 | 账单分析与证据追溯 |
| 联系人 | 姓名、别名、手机号和已验证的收款账户绑定 | 收款人匹配 |
| 账单及代扣协议 | 对象、到期日、金额、状态、生效时间、取消能力 | 订阅与未来支出 |
| 预测假设 | 金额、日期、来源、是否预计、用户修正 | 现金流情景 |
| 目标及分配 | 目标金额、日期、优先级、资金归属、关联任务 | 目标冲突与进度 |
| 任务与回执 | 步骤依赖、确认版本、状态、交易标识、结果 | 中断恢复与结果核查 |

P0 仅支持人民币，统一使用 Asia/Shanghai 业务日期和日累计口径。采用明确的模拟时钟展示跨日任务，界面持续显示“演示时间”，不能把时间快进包装为真实日期。

提供固定样例数据、样例场景恢复能力及演示时钟。重置演示数据仅作用于当前沙箱样例，并提示会清除该样例的模拟操作。

页面固定显示“沙箱演示环境，无真实资金”，预测标注数据时间及假设。规划功能不要求理财产品快照，避免把未使用的数据采集列为首版依赖。

## 14 三条完整验收与演示流程

### 14.1 主流程 购买电脑的资金安排

以下金额为验收样例，不是个人投资或消费建议。

演示日期为 2026-10-01。工资账户可用余额 9000 元；10 月 5 日房租 3000 元；10 月 8 日还款 2000 元；10 月 1 日至 9 日的生活预算合计 1200 元；10 月 10 日预计工资 10000 元；用户希望工资账户保留 800 元缓冲。本人储蓄账户初始余额为 0。

1. 用户说“我想买 6000 元的电脑，房租和还款不能受影响”。Agent 追问或确认目标日期，生成目标草稿。
2. 现金流试算显示：工资到账前预计剩余 9000 − 3000 − 2000 − 1200 = 2800 元；若现在支付 6000 元，将出现预计 3200 元缺口。提示这是未来预测，不把当前余额 9000 元说成当前不足。
3. 展示两种安排：保留 6000 元目标，待工资实际到账后备齐；或保留工资前完成的时间要求，将目标调整为不超过 2000 元，从而保留 800 元缓冲。后者明确意味着降低目标预算，需要用户选择。
4. 用户选择第一种，计划现在向本人储蓄账户转入 2000 元，工资实际到账后再转 4000 元。逐笔转账按日累计规则强验证，不因“本人账户”跳过策略。
5. 首笔成功后，工资账户余额为 7000 元，储蓄账户为 2000 元，合并余额仍为 9000 元。在预设支出发生后，工资前工资账户预计低点为 800 元，合并余额为 2800 元。目标已备资金 2000 元，不能在合并预测中再次减去同一笔转账。
6. 演示时钟推进至工资日。模拟银行确认工资实际到账后，生成第二笔待确认转账；用户确认并验证后执行。若工资未到账，该步骤暂停，并展示调整方案。
7. 两笔转账都成功后，目标显示“资金已备齐 6000 元”。系统不显示“电脑已购买”。

展示重点：自然语言目标、逐日预测、方案比较、本人账户调配、强验证、条件触发与持续跟踪。

### 14.2 订阅处理流程

1. 用户询问近期有哪些自动扣费，系统按权限要求展示已核实协议和疑似周期扣费。
2. 用户选择取消一项协议，页面说明银行代扣与商户订阅的区别，展示实际支持的操作。
3. 用户确认，模拟接口返回取消成功和生效日期。
4. 未来预测从生效日期起移除相应扣费；若用户正在进行资金目标，显示“可重新分配的预计余额变化”，不自动扩大转账金额。
5. 另选一个不支持取消的商户，系统提供办理指引并维持待处理状态。

### 14.3 异常交易与卡片处理流程

1. 账单分析提示一笔需要核查的交易，展示异常依据及所属卡片。
2. 用户表示不是本人熟悉的交易，系统提供核查和冻结入口，不直接下诈骗结论。
3. 用户确认临时冻结后，卡片状态真实更新；相关计划显示受影响事项。
4. 用户申请解冻或挂失时执行强验证。验证失败不改变卡片状态。
5. 用户可查看该次操作记录，无法操作其他用户卡片。

## 15 验收标准与效果验证

### 15.1 P0 发布门槛

| 类别 | 必须通过的标准 |
|---|---|
| 六模块闭环 | 六个模块各至少完成一个从输入到结果的流程，而非仅有入口和静态卡片 |
| 转账正确性 | 金额及对象正确，成功回执可查询；重复确认不重复扣款；未知结果先核查 |
| 授权正确性 | 绿黄红规则符合测试样例；未确认和验证失败不执行；修改关键字段后旧授权失效 |
| 跨用户隔离 | 通过页面、自然语言或直接业务请求均不能查询或修改他人对象 |
| 累计与并发 | 连续三笔 400 元时第三笔升级验证；跨会话和并发不能绕过累计策略 |
| 账单口径 | 图表和明细一致；互转、信用卡还款及关联退款正确处理 |
| 订阅边界 | 疑似与已核实分开；不支持的取消不报成功；成功取消按生效日期更新预测 |
| 卡片状态 | 冻结、解冻、挂失与查询结果一致，影响范围与模拟银行规则一致 |
| 现金流准确性 | 固定样例的金额、余额低点、日期及情景切换计算正确；缺数据和预计收入明确标注 |
| 目标资金归属 | 多目标分配不重复占用同一资金；本人账户划转不重复扣减合并资金 |
| 任务恢复 | 刷新页面或重新进入可恢复任务；定时到期、超时和取消状态明确；已成功步骤不重做 |
| 安全输入 | 直接提示词及交易备注中的恶意指令不能绕过访问控制、确认和验证 |
| 模拟与真实区分 | 页面、验证、银行回执、演示时钟均明确标注模拟性质 |

安全门槛要求预先定义的用例全部通过，并记录覆盖范围，不将有限用例通过宣传为抵御所有攻击。

### 15.2 可用性验证

在条件允许时邀请至少 5 名未参与开发的同学完成转账、订阅取消、卡片冻结及目标创建。记录任务完成率、主动操作次数、完成时间和误解点，特别检查能否区分“已到账与预计”“计划分配与实际转账”“终止代扣与取消订阅”。

P0 的建议目标是至少 4 人能在不口头指导的情况下完成上述核心流程。该目标为验收建议，未测试前不写成已取得的效果。业务验证步骤不得为了追求“一句话完成”而省略。

### 15.3 体验与可运行性

操作发起后应立即给出可见反馈；较慢任务显示进行中状态和取消等待入口。超时不能转成默认成功，具体超时阈值在接口条件明确后确定。

以桌面浏览器为主要验收环境，窄屏下核心表单和确认卡可用。关键状态除颜色外使用文字说明。数据更新时间、空状态、失败状态和无权限状态均需有明确页面表现。

提供可运行的沙箱服务、评审可调用的业务入口与操作记录导出，部署方法在技术方案中另行描述，不在 PRD 冻结具体框架。
