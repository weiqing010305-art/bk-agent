## 1 怎样开始

目前设计材料可以支撑接口评审、初始化工程和第一条业务闭环。建议先核对核心对象、金额单位及操作状态，再按本清单顺序开发；不需要继续扩充新的功能文档才开始。

第一条可运行闭环为：演示登录 → 查询账户 → 表单创建转账草稿 → 核对 → 模拟强验证 → 模拟银行记账 → 回执 → 刷新余额。它先验证身份、接口、数据和授权链路，再接入自然语言发起同一个操作。

模型供应商和精确依赖补丁版本尚需在初始化时落实。没有模型凭据时可先使用显式回放模式联调，实时 Agent 验收保持未通过状态，不能以回放冒充模型理解能力。

契约固定后前端可用同契约 fixture 实现页面，银行及授权模块可独立推进；接口差异必须先改契约再改两端，避免每个模块各定义一份状态枚举。

## 3 每阶段需要交付什么

### 阶段 A 第一条转账闭环

完成 W00–W03 的最小范围。输出可运行服务、账户与转账 API、初始前端、基础测试和版本锁文件。标准是确实改变模拟银行余额并能查询回执，而非前端显示一张成功卡。

这一阶段需要把重复点击、验证失败、修改金额、跨用户 ID 和三笔 400 元等问题跑通。它们影响所有后续功能，不留到最后集中处理。

### 阶段 B 四项基础能力与自然语言

完成 W04–W06。Agent 能提出规范业务草稿，订阅和卡片正确区分实际能力，账单口径可追溯。模型离线时基础表单可用。

### 阶段 C 两项新增能力

完成 W07–W09，交付现金流、目标方案、资金分配和可恢复任务。验证关闭网页和重启服务后仍能找到任务；工资没到账不执行依赖转账。

### 阶段 D 发布候选

完成 W10–W11。对照冻结用例、实际测试环境和演示路径形成结果报告。报告区分通过、失败、未执行和受限，不能只写“全部正常”。

## 5 三条现场演示脚本

### 主线 目标资金安排

1. 使用 fixture A，先展示 9000 元可用余额和未来账单。
2. 输入“想买 6000 元电脑，房租和还款不能受影响”，补齐希望日期。
3. 对比立即支出的 -3200 元低点和两套方案，选择分两阶段安排。
4. 保存目标，单独确认并验证首笔 2000 元转账，显示回执及目标进度。
5. 展示工资账户低点 800 元、合并低点 2800 元，解释本人互转不减少总资产。
6. 通过演示时钟推进已登记银行事件；工资实际入账后，在任务中心确认第二笔 4000 元。
7. 展示资金已备齐；另一次独立运行模拟工资延迟，演示暂停和调整。

### 辅线 订阅管理

使用 fixture B。先展示疑似候选，确认后查询协议，再取消一项受支持代扣，展示生效后的预测变化。对未接入商户展示指引和待处理状态，解释不同能力范围。

### 辅线 卡片与执行可靠性

使用 fixture C 展示异常候选、交易证据及卡片冻结。使用 D 独立演示重复确认和结果未知后的核查，展示实际银行只发生一笔交易。不要同时混入不同 fixture 的余额数字。

## 6 团队协作约定

金额统一整数分；接口、状态和错误码以技术方案为准。前端不自行推断授权状态，Agent 不直接写业务数据库，银行服务不依赖模型决定交易是否合法。

每个工作包交付包括变更、依赖、用例结果及已知限制。变更契约时更新 OpenAPI 快照、前端类型、fixture 和受影响测试，不能只口头通知。

任务中心和 UNKNOWN 处理是第一条转账闭环可靠性的延伸，不当作有空再做的视觉功能。到期任务保持人工确认，不通过演示快进绕过授权。

本轮只完成开工资料。下一阶段可以从 W00–W03 启动实际开发；具体人员映射和日期由团队投入确定，不在本文虚构承诺。
