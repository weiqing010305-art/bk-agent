## 1. 权限分级实现说明

### 1.1 三级分档与赛题的对应

| 赛题原文 | 我们的实现 | 界面表现 |
|---|---|---|
| 余额查询、交易记录查询、账单分析、理财收益查询等纯查询，**确认意图后直接执行，无需二次确认** | `RISK.LOW`，`requires: []` | 静默执行，不弹任何东西 |
| 小额转账（日累计 ≤1000 元）、订阅查询、虚拟卡申请等，**执行前展示操作详情并获得确认** | `RISK.MEDIUM`，`requires: ['confirm']` | 弹出操作详情，用户点确认 |
| 大额转账（>1000 元）、密码修改、卡片挂失解挂、理财产品申购等，**须人脸识别、短信验证码或 U 盾等多因子认证** | `RISK.HIGH`，`requires: ['sms','face','token']` | 进多因子认证弹窗，三种方式都可走通 |

实现位置：`src/services/policy.js`。操作目录 `OPERATIONS` 已登记 19 个操作，覆盖赛题列出的全部业务。

### 1.2 三条设计不变量（这是分级的可信来源）

**① 风险等级不由调用方声明。**

`assess({ op, amount, todayTotal })` 只接受「要做什么」和「多少钱」，
**不接受「这有多危险」**。调用方就算传入 `level: 'low'` 也不影响判定 —— 有测试守着这条：

```js
test('调用方无法把高风险操作声明成低风险 —— 风险只由操作类型推出', () => {
  const r = assess({ op: 'password.change', level: 'low', risk: 'low', trusted: true });
  assert.equal(r.level, RISK.HIGH);
});
```

这条不变量是**注入防御的第一层**，而且是结构性的：任何一段 Prompt 都无法让一个高风险操作
变成低风险，因为"降级"这个动作在 API 上不存在。

**② 分档依据是「日累计」而不是单笔。**

赛题写的是「日累计 ≤1000 元」。如果按单笔判，用户分两笔 600 元就能绕过。
`todayTotal` 由调用方从账本算出后传入，`assess` 判的是 `todayTotal + amount`：

```js
test('风险按「当日累计」判定，不是按单笔 —— 分两笔绕不过门槛', () => {
  assert.equal(assess({ op: 'transfer.small', amount: 60000, todayTotal: 0 }).level, RISK.MEDIUM);
  assert.equal(assess({ op: 'transfer.small', amount: 60000, todayTotal: 60000 }).level, RISK.HIGH);
});
```

**③ 未知操作不放行，也不降级。**

白名单之外一律按最高风险处理，并且超单笔上限直接拒绝而不是"升级验证"。

### 1.3 多因子认证（三种方式都可演示）

| 方式 | 演示交互 | 说明 |
|---|---|---|
| 短信验证码 | 输入 6 位码 | 演示码固定并明写在界面上 —— **不假装这是真验证** |
| 人脸识别 | 点击后 1.8 秒活体检测进度 + 扫描动效 | 模拟 |
| U 盾 | 长按 1.2 秒 | 模拟 |

实现位置：`src/components/AuthDialog.jsx`。

### 1.4 分级的落点在界面上可验证

- 查询类：说「这个月花了多少」，**没有任何确认弹窗**
- 中风险：转 300 元，弹出操作详情
- 高风险：转 2000 元，进多因子认证

## 2. 安全机制实现说明

### 2.1 注入防御（纵深两层）

**第一层是结构性的，不是文本检测的：**

| 结构约束 | 效果 |
|---|---|
| Agent 不产出任何事实数字，只产出 `{path}` 引用 | 无法通过对话让 Agent"编造"一个余额 |
| 所有操作必须在 `OPERATIONS` 白名单里 | 白名单外的操作按最高风险处理 |
| 风险由操作类型 + 金额 + 日累计推出 | **"降级"这个动作在 API 上不存在** |
| 引用解析不到时显示占位符，绝不退回猜测值 | 幻觉不会变成看似合理的数字 |
| 每个 surface 带 `provenance` | 数据来源可追溯 |

**第二层是 `src/services/guard.js` 的文本筛查**，拦下明显越权意图并留痕：

- 越权类：忽略规则、跳过验证、直接转账、提升权限、角色扮演、system 前缀、开发者模式
- 诱导类：编造/伪造/假装一个余额、随便给个数字

两层的关系要在答辩时讲清楚：**就算第二层被完全绕过，第一层仍然有效**。

### 2.2 幻觉防护

沿用 §2.1 的引用机制。额外一条：`agent/planner.js` 里有一组测试守着
「组件结构里不含写死的事实数字」—— 曾经真的违反过，被测试抓到。

### 2.3 操作审计（决策链路与执行日志）

实现位置：`src/services/audit.js`。

记录的不只是「谁在什么时候做了什么」，而是**为什么允许它发生**：

| 字段 | 含义 |
|---|---|
| `kind` | intent / policy / execute / blocked / auth |
| `input` | 用户原话（注入检测要留证） |
| `intent` | 识别出的意图 |
| `op` / `risk` | 命中的操作与判定的风险等级 |
| `decision` | 允许 / 拒绝 / 需确认 / 需多因子 |
| `detail` | 人话说明，含「今日已转 ¥X」这类判定依据 |

环形缓冲 200 条，结构按可落库设计（每条自带 id / seq / at）。

### 2.4 安全锁定

- **连续 3 次验证失败** → 锁定
- **连续 2 次可疑输入** → 锁定
- 锁定后界面顶部出现横幅，**只能手动解除**（不给自动解锁，避免暴力尝试）

### 2.5 沙箱

**已知缺口，见 §3。**

## 3. 已知风险清单（必交部分，如实写）

| # | 风险 | 严重度 | 现状 | 缓解 |
|---|---|---|---|---|
| R1 | **没有真实 LLM**，意图理解是规则引擎 | 中 | 演示环境 | 接口已隔离在 `parseIntent`，换成 LLM 只改这一个函数；答辩时如实说明 |
| R2 | **沙箱隔离未实现**。赛题要求「生成的代码在受限可监控的逻辑隔离环境中运行」，本项目没有代码执行场景 | 中 | 未实现 | 如实说明本项目不生成并执行代码；若被追问，给出 Monzo 的「受限工具子集」定义作为设计方向 |
| R3 | **注入检测是正则**，可被改写绕过 | 中 | 已实现但非完备 | 明确它是第二层；第一层是结构性白名单。正则只负责拦住明显案例并留痕 |
| R4 | **多因子是模拟的**，短信码固定可见 | 低 | 演示环境 | 界面上明写「演示环境验证码」；不假装是真实认证 |
| R5 | **审计日志只在内存**，刷新即失 | 低 | 环形缓冲 | 结构按可落库设计；演示项目不落库 |
| R6 | **余额是单值**，并发转账可能超限 | **高** | 修复中 | 调研报告指出 `validateTransferSlots` 只读校验不写余额，并发必然超限。已排期拆成 available / frozen / pending |
| R7 | **两个入口各自成体系**，产品层与 Agent 层的状态一致性靠账本单一来源保证 | 低 | 已收敛 | `ctx.setBank` 是唯一写入口；页面不得自开 localStorage 覆盖层（此规则曾经被违反过两次，已修） |
| R8 | **前端不校验任何真实凭证** | 低 | 设计如此 | 演示环境，无真实资金 |

### 3.1 我们主动放弃的（而不是没想到）

- **不做真实生物识别**：没有硬件与合规资质，做假的比不做更糟
- **不做真实加密传输**：演示环境无后端
- **不做风控模型**：赛题未要求 ML，规则引擎可解释性更强，且每条规则都能输出决策链路证据

## 4. 与行业对标的差异（答辩可用）

调研发现（`doc/research/revolut-ai-and-za-deep-dive.md`）：

- **Revolut AIR 只有两级**：查询类零授权，执行类一律生物识别。
  官方原文：「AIR cannot perform sensitive actions without your biometric approval」。
- **我们的中风险档是相对 AIR 的增量**，且是**赛题明确要求的**（「小额转账……展示操作详情并获得确认」）。
- ZA Bank 把两级风控写进 slogan：「5 seconds recall, facial authentication」——
  与我们「5 秒可撤销窗口 + 多因子」一致。
